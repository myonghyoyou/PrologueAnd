## 1. 개요 및 목적

### 1.1 한 줄 정의
> 잠재 고객이 자신의 업무 문제를 발견하고 → Prologue&이 실제로 해결할 수 있다고 믿고 → 프로젝트 문의까지 진행하도록 만드는 **브랜드/서비스 사이트**

### 1.2 브랜드
- 최상위 브랜드명: **Prologue&**
- 핵심 문장: **복잡한 업무를 단순한 제품으로 바꿉니다.**
- 공식 포지션: **B2B Product Engineer**
- 세부 영역: Workflow Design × B2B UX × Product Engineering × Automation/AI

### 1.3 이 사이트가 아닌 것
- 개발자 채용용 기술 포트폴리오가 아니다.
- 기술 스택을 전면에 내세우는 사이트가 아니다.
- 단순 프로젝트 갤러리가 아니다.

### 1.4 절대 전제 (00_README)
1. 브랜드의 최상위 이름은 `Prologue&`이며 모든 채널의 식별자는 여기에 축적한다.
2. 주 고객은 개발자가 아니라 **업무 시스템 개선·MVP 개발·사내 도구 구축이 필요한 잠재 고객**이다.
3. 기술 스택보다 **Problem → Workflow → UX → Product → Impact** 순서를 우선한다.
4. 핵심 전환 목표는 조회가 아니라 **프로젝트 문의**다.
5. 문의에서 반복되는 문제를 수집해 **Vertical SaaS 후보**로 발전시키는 통로로 쓴다.
6. 실제 업무 프로젝트는 **공개 권한·NDA·IP·개인정보**를 먼저 검토하고, 필요 시 익명화하거나 Mockup으로 재구성한다.

## 2. 타깃 사용자와 핵심 문제

### 2.1 1차 타깃 (문의 전환 대상)
| 유형 | 상황 | 대응 서비스 |
|---|---|---|
| 업무 시스템 담당자 | ERP·관리자 시스템·병원·제조·건설·사내 시스템이 기능은 많지만 쓰기 어려움 | 서비스 A: 기존 시스템 UI/UX·Workflow 개선 |
| 반복 수작업 조직 | 엑셀·종이·카톡·메일 중심으로 업무가 흩어져 상태 추적이 어려움 | 서비스 B: 업무의 웹 시스템화 |
| 아이디어 보유자 | 아이디어는 있으나 Workflow·UX·MVP 구조가 없음 | 서비스 C: 아이디어 → MVP |

### 2.2 2차 타깃
- 블로그·Threads·크몽에서 유입되어 신뢰를 확인하러 오는 방문자
- 크몽 구매 전 포트폴리오를 검증하는 구매자

### 2.3 사용자 특성 (설계 제약)
- 개발 지식이 없다 → 기술 용어 최소화, 업무 언어로 설명
- 모바일(Threads·카톡 링크)로 처음 접할 확률이 높다 → 모바일 우선
- 연령대가 넓고 고령 사용자가 포함될 수 있다 → 가독성·대비·터치 영역 기준 준수
- 상사·동료에게 공유할 수 있다 → 링크 미리보기(OG)와 인쇄 가독성 고려

### 2.4 홈에서 제시할 4가지 문제 (05 §Section 2)
1. 복잡한 업무 — 엑셀·메신저·이메일·구두 요청으로 흩어진 업무
2. 불편한 기존 시스템 — 기능은 있지만 직원이 쓰기 어려운 화면
3. 종이·수작업 — 단순 복사가 아닌 구조 개선이 필요한 디지털화
4. 제품화가 필요한 아이디어 — Workflow·UX·MVP 구조가 없는 아이디어

## 3. 성공 지표

### 3.1 전환 깔때기 (04 §9)
콘텐츠 조회 → 프로필 방문 → Portfolio 클릭 → **문의** → 상담 → 견적 → 계약

### 3.2 사이트 KPI (06)
| 지표 | 측정 방법 |
|---|---|
| Portfolio 방문 수 | Analytics 페이지뷰 |
| Case Study 조회 수 | `/work/*` 페이지뷰, 스크롤 깊이 |
| 문의 수 | 문의폼 제출 이벤트 |
| 문의 → 계약 전환율 | 고객 문제 DB의 계약 여부 필드 |
| 프로젝트별 문의 기여도 | 문의폼의 유입 경로·참조 Case Study 필드 |
| 반복 등장한 고객 문제 수 | 고객 문제 DB 집계 |

팔로워·단순 조회보다 문의·계약에 가까운 지표를 우선한다.

### 3.3 사업 맥락 (02 §3)
사이트 자체의 수익 목표는 없다. 사이트는 "첫 결제 → 10~30만 원 → 50~100만 원 → 200~300만 원 → 300~500만 원" 단계로 가는 문의 유입 장치다.

### 3.4 출시 판정 기준
- 4개 Case Study 중 최소 2개 게시 (Por favor Harry, Daeryun Learning Hub 우선)
- 문의폼 제출 → 이메일 수신 + 스프레드시트 적재가 실제로 동작
- 모바일 400px 폭에서 가로 스크롤 없음
- Lighthouse 모바일 Performance·Accessibility·SEO 90 이상

### 4.3 Work 목록
- 4개 프로젝트를 03의 역할 구분과 함께 노출
- 정렬은 고정 순서: Por favor Harry → Daeryun Learning Hub → 병원 UI/UX → Custom Commerce

### 4.4 Case Study 상세 (공통 템플릿, 03 §5)
모든 Case Study는 아래 10개 섹션을 같은 순서로 가진다. 섹션 제목과 앵커 id를 고정해 페이지 간 구조가 동일하게 보이도록 한다.

1. Overview — 프로젝트 한 줄 정의, 역할, 기간, 사용자
2. Problem — 기존 문제
3. Existing Workflow — 기존 흐름(다이어그램)
4. Insight — 핵심 한 문장
5. Redesign — 재설계한 흐름(다이어그램)
6. Solution — 실제 화면/기능
7. Before / After — 대응 이미지 세트
8. Impact — 정성/정량 성과
9. What I Learned
10. CTA — "비슷한 문제가 있다면" → 문의폼(프로젝트 참조값 자동 전달)

하단 보조 정보: `Built with` (기술 스택). 상단에는 기술을 노출하지 않는다. Custom Commerce만 Architecture Diagram을 Solution 안에 포함해 상대적으로 더 강조한다.

### 4.5 Services
- 서비스 A/B/C 각각: 대상 상황, 진행 흐름, 산출물, 문의 CTA
- 가격은 사이트에 표기하지 않는다(크몽에서 상품별로 명시). 단, "범위·수정 횟수·산출물" 항목은 크몽 등록 시 재사용할 수 있도록 데이터로 관리한다.

### 4.6 About·Contact
- About: B2B Product Engineer로서의 역할, 문제 해결 패턴 7단계(01 §3), 잘 맞는 일(01 §5)
- Contact: 문의폼 (§6)

## 5. Case Study 콘텐츠 요구사항

### 5.1 프로젝트별 증명 역할 (03)
| 프로젝트 | 핵심 증명 | 핵심 메시지 |

| Por favor, Harry | Workflow Design / Product Thinking | ToDo를 만든 것이 아니라 요청 Workflow를 바꿨다 |

| Custom Commerce | End-to-End Product Engineering | 기성 솔루션 없이 전체 서비스 Flow를 설계·구현했다 |

### 5.2 프로젝트별 필수 자산 (06 Week 2~5)
| 프로젝트 | 필수 자산 |
|---|---|
| Por favor, Harry | Before/After Workflow Diagram, 요청폼·심사 Queue·진행 상태·약속일·Dashboard·요청자 조회 화면, 대표 이미지 |
| Daeryun Learning Hub | 종이 학습 Flow / 웹 학습 Flow 시각화, 핵심 화면, 대표 이미지 |
| 병원 UI/UX | 개선 전/후 대응 화면 최소 3세트, 각 화면의 목적·사용빈도·주요 사용자·문제·변경 이유·현업 피드백 |
| Custom Commerce | 실제 구현 기능 Inventory, 사용자 Flow, 관리자 Flow, Architecture Diagram, 직접 구축 이유, 핵심 의사결정 |

### 5.3 콘텐츠 관리 방식
- Case Study 본문은 **MDX 파일**로 관리한다 (`content/work/<slug>.mdx`). 코드 배포 없이 텍스트만 수정 가능하고, 블로그·Threads 재활용(04 §7) 시 원천 텍스트로 쓴다.
- frontmatter 필수 필드: `title`, `tagline`, `tags[]`, `role`, `period`, `order`, `published`, `ogImage`, `builtWith[]`
- 이미지는 `public/work/<slug>/` 아래에 두고, 공개 불가 화면은 Mockup으로 재구성한 파일만 커밋한다.

### 5.4 공개 전 확인 체크리스트 (프로젝트별, 06 Week 1 §2)
회사명 / 실제 화면 / 사용자 데이터 / 내부 URL / 업무 프로세스 / NDA / IP / Mockup 재제작 필요 여부
→ 확인 결과를 각 MDX frontmatter의 `disclosure` 필드에 기록한다 (`full` / `anonymized` / `mockup`).

## 6. 문의 Conversion Flow

### 6.1 목표
상담 전에 고객 문제의 **60~70%를 파악**한다. 문의 단계에서 고객이 스스로 문제를 구조화하도록 만든다.

### 6.2 문의폼 필드 (05 §7, 06 Week 1 §4)
| 순서 | 필드 | 유형 | 필수 |
|---|---|---|---|
| 1 | 현재 어떤 업무를 하고 있나요? | 장문 텍스트 | 필수 |
| 2 | 지금 어떤 도구를 사용하고 있나요? | 복수 선택(엑셀/종이/카톡·메신저/이메일/기존 시스템/기타) + 텍스트 | 필수 |
| 3 | 가장 불편한 부분은 무엇인가요? | 장문 텍스트 | 필수 |
| 4 | 이 업무를 몇 명이 사용하나요? | 단일 선택(1~5 / 6~20 / 21~100 / 100+) | 필수 |
| 5 | 얼마나 자주 반복되나요? | 단일 선택(매일/매주/매월/비정기) | 필수 |
| 6 | 기존 시스템 개선인가요, 신규 구축인가요? | 단일 선택(개선/신규/모름) | 필수 |
| 7 | 원하는 결과는 무엇인가요? | 장문 텍스트 | 선택 |
| 8 | 희망 일정 | 단일 선택(1개월 내/3개월 내/6개월 내/미정) | 선택 |
| 9 | 예산 범위 | 단일 선택(미정 포함) | 선택 |
| 10 | 연락처 (이메일 필수, 전화 선택) | 텍스트 | 필수 |
| 숨김 | 유입 경로(referrer), 참조 Case Study(slug), 제출 시각 | 자동 | — |

- 폼은 2단계로 나눈다: 1단계(문제 1~6) → 2단계(목표·일정·예산·연락처). 첫 단계에서 이탈해도 부분 데이터는 저장하지 않는다(개인정보 최소 수집).
- 제출 성공 시 같은 화면에서 "접수됨" 상태와 답변 예상 시점을 보여준다. 페이지 이동 없음.
- 실패 시 원인과 대안(이메일 주소 직접 표기)을 보여준다.

### 6.3 수신·저장 (결정됨)
- **이메일 알림**: 제출 즉시 운영자 이메일로 전문 발송
- **스프레드시트 적재**: Google Sheets에 1행 추가. 컬럼은 문의폼 필드 + 고객 문제 DB 필드(04 §10: 업종·사용자 유형·현재 해결방식·가장 힘든 단계·빈도·도구·기대효과·예산·계약 여부·미계약 사유)로 구성해 문의가 그대로 고객 문제 DB가 되게 한다.
- 계약 여부·미계약 사유 컬럼은 운영자가 수동 기입한다.

### 6.4 스팸·오남용 방지
- 서버 측 검증 + honeypot 필드 + 제출 속도 제한
- CAPTCHA는 도입하지 않는다(전환 저해). 스팸이 실제로 발생하면 재검토.

## 7. 브랜드·디자인 요구사항

### 7.1 브랜드 표기
- 기본 표기: `Prologue&`
- 문장 표기: `Prologue& — 복잡한 업무를 단순한 제품으로 바꿉니다.`
- 하위 명칭(`Prologue& Studio`, `Prologue& Work`)은 사이트 v1에서 사용하지 않는다.
- 피할 표현: UI/UX 개발자, React 개발자, 프론트엔드 외주 개발자, 혁신적인 Product Engineer, 디지털 혁신 전문가

### 7.2 로고 자산 사용 규칙 (`data/images/logo/`)
| 변형 | 용도 |
|---|---|
| `[color]P& black` | 라이트 배경 헤더·푸터·OG 이미지 기본 |
| `[color]P& white` | 다크 배경(다크 섹션, 다크 모드) |
| `[mono]P& black/white` | 단색만 허용되는 곳(인쇄, 워터마크, 흑백 컨텍스트) |
| `[color]P&simple` / `[mono]P&simple` | 파비콘, 앱 아이콘, 소셜 프로필, 카드 뱃지, 32px 이하 축소 표기 |

- 사이트 구현 시 PNG를 그대로 쓰지 않고 SVG로 변환한다(선명도·다크 모드 전환·용량).
- 워드마크의 `&` facet 요소는 브랜드의 유일한 장식 요소로, 디자인 시스템 확장의 기준점이 된다(08 참조).
- 최소 표시 크기: 워드마크 가로 120px, 심볼 24px. 그 이하에서는 심볼만 사용.

### 7.3 디자인 방향 (미확정 — 시안 제작 후 결정)
`08_design_directions.md`의 5개 후보안 중에서 **시안을 제작해 비교한 뒤** 확정한다.
후보: ① 에디토리얼 미니멀 ② 블루프린트 ③ 딥 네이비 프로덕트 ④ 스위스 구조주의 ⑤ 종이에서 제품으로

어떤 안을 택하든 아래는 공통 요구사항이다.
- 색: 흑/백 + 로고 네이비(`#2B3160`)·스틸블루(`#7A8AA6`) 계열을 기본으로 하고 액센트는 1색을 넘기지 않는다.
- 타이포: 한글 본문은 Pretendard. 헤드라인 서체는 안별로 다름.
- 본문 줄 길이 80자 이하, 본문 크기 모바일 16px 이상.
- 고령 사용자 가독성: 본문 대비 WCAG AA(4.5:1) 이상, 터치 영역 44px 이상.
- AI 생성 티가 나는 기본값 회피: 크림 배경+테라코타, 검정+형광 액센트, 동일 카드 벤토 그리드, 모든 제목 위 대문자 eyebrow, 섹션마다 fade-up 모션.
- 모션은 `09_interaction_references.md` §4.3의 "화려함 예산" 안에서, 내용을 설명하는 모션만 허용(핀 고정 구간 페이지당 1개, 스크롤 연동 2개 이하). 장식 목적의 섹션 페이드인·카드 호버 확대는 금지. `prefers-reduced-motion` 준수.

### 7.4 반응형
- 기준 폭: 400px(모바일) / 768px / 1200px
- 모바일에서 우선 노출: Hero 문장 → CTA → Problems → Featured Work. Services·About은 접힘 허용
- 표·다이어그램·코드만 `overflow-x: auto` 컨테이너 허용, 페이지 본문 가로 스크롤 금지

## 8. 기술 요구사항

### 8.1 스택 (결정됨)
| 영역 | 선택 | 이유 |
|---|---|---|
| 프레임워크 | **Next.js (App Router)**, TypeScript | 정적 생성 + 문의폼 Route Handler를 한 프로젝트에서 처리. Vercel 배포와 궁합 |
| 콘텐츠 | MDX (`content/work/*.mdx`) | Case Study 텍스트를 코드와 분리, 재활용 용이 |
| 스타일 | CSS Modules 또는 Tailwind — 디자인 시안 확정 후 결정 | 안별로 필요한 표현력이 다름 |
| 다이어그램 | SVG(정적 파일 또는 React 컴포넌트) | 다크 모드·반응형 대응, 화질 |
| 폼 처리 | Next.js Route Handler → 이메일 발송(Resend 등) + Google Sheets API | §6.3 |
| 이미지 | `next/image`, WebP/AVIF | 성능 |
| Analytics | Vercel Analytics 또는 GA4 (문의 이벤트 추적 필수) | §3.2 |
| 호스팅 | **Vercel** + 커스텀 도메인(예정) | 결정됨 |

### 8.2 SEO·공유
- 페이지별 `title`·`description`·OG 이미지 (Case Study는 개별 OG 이미지)
- `sitemap.xml`, `robots.txt`
- 구조화 데이터: `Organization`(Prologue&), Case Study는 `Article`
- 한국어 기본(`lang="ko"`), 영문 페이지는 v1 범위 밖

### 8.3 접근성
- 키보드 포커스 가시성, 시맨틱 heading 구조, 이미지 대체 텍스트(Before/After는 차이를 설명하는 alt)
- 색만으로 정보를 구분하지 않음(Before/After 라벨 필수)

### 8.4 성능 목표
- LCP 2.5초 이하(모바일 4G), CLS 0.1 이하
- 초기 JS 최소화: 인터랙션이 필요한 곳(문의폼, 다이어그램 전환)만 클라이언트 컴포넌트

### 8.5 기술 스택의 노출 위치
- Case Study 하단 `Built with` 항목에만 표시
- Home·Services에서는 기술명을 노출하지 않는다
