## 1. 규칙 (이 사이트의 문구는 전부 이 기준으로)

| # | 규칙 | 예 (전 → 후) |
|---|---|---|
| R1 | **번역투 조사·구문 금지**: "~를 통해", "~에 있어서", "~에 대해", "~에 의해", "~되어지다", 이중 조사("~에서의") | "요청 단계에서 필수 정보를 채우게 해" → "요청할 때 꼭 필요한 정보를 채우게 해서" |
| R2 | **줄표(—) 쓰지 않기**. 마침표·쉼표·괄호로 | "Design · Build — 설계와 구현이…" → "Design · Build. 설계한 그대로 만듭니다." |
| R3 | **영어 직역 관용구 금지**: "2영업일 이내", "넘기세요(swipe)", "당신의", "~하실 수 있습니다" 남발 | "2영업일 안에 답변드립니다" → "이틀 안에 답장드리겠습니다" / "→ 넘기세요" → "휠을 굴리거나 → 키를 누르면 다음 장으로" / "당신의 업무" → "문의" |
| R4 | **평소 말로**: 한자어 명사 나열보다 동사로. "구조화된 요청폼" → "요청 양식", "약속일 확정" → "처리 예정일 확정", "상태 자동 공유" → "진행 상황 자동 안내", "요청자" → "요청한 사람", "조회" → "확인" |
| R5 | **제품 안 영어 용어는 한국어로**(브랜드 고유어 제외): "심사 Queue" → "심사 대기열", "Dashboard" → "현황판", "요청폼" → "요청 양식". 남기는 영어: Prologue&, Projects, Case Study, Before/After, Understand~Improve(단계 이름), Workflow·UX(포지션 표기에서만) |
| R6 | **"A가 아니라 B" 대구는 한 화면에 하나까지** | Case Study Insight 한 곳만 유지 |
| R7 | **선택지·라벨은 말하듯이**: "정해지지 않음" → "아직 정하지 않았어요", "상담 후 결정" → "이야기 나눠 보고", "기존 개선 / 신규 제작 / 모르겠음" → "쓰던 걸 고치기 / 새로 만들기 / 잘 모르겠어요" |
| R8 | **과장·상투 삭제**: "혁신", "최적", "완벽", "시사하는", "주목할 만한" 금지 (`01` §8과 같음) |
| R9 | **존댓말 한 종류**: 방문자에게는 "~합니다/~해요" 섞지 않고 "~합니다"로 통일, 서랍의 질문은 "~하세요?"로 |
| R10 | 은유 술어 금지("걷어낸다"는 허용 범위, "삼킨다·목을 조인다" 류 금지) |

## 2. 이번에 고친 문구 (주요)

| 위치 | 전 | 후 |
|---|---|---|
| 히어로 보조문 | 기업의 업무 시스템부터 … — 만들기 전에 정리하고, 실제로 쓰이는 끝까지 함께합니다. | 회사 업무 시스템부터 개인 맞춤 개발, 직접 만드는 서비스까지. 만들기 전에 먼저 정리하고, 실제로 쓰일 때까지 함께합니다. |
| 히어로 힌트 | → 넘기세요 (휠 · 트랙패드 · 방향키) | 휠을 굴리거나 → 키를 누르면 다음 장으로 |
| 처음 | Understand · Simplify — 현재 업무와 사용자를 이해하고, 불필요한 단계부터 걷어냅니다. | Understand · Simplify. 지금 일이 어떻게 돌아가는지 보고, 없어도 되는 단계부터 덜어냅니다. |
| 그리고 | Design · Build — 설계와 구현이 끊기지 않고 이어져, 처음 정리한 문제가 끝까지 흐트러지지 않습니다. | Design · Build. 설계한 그대로 만듭니다. 처음에 정리한 문제가 중간에 흐려지지 않게. |
| 끝까지 | Improve — 사용 후에 드러나는 문제를 반복해서 고칩니다. | Improve. 써 보면서 나오는 문제를 계속 고칩니다. |
| 회사든 개인이든 | …나만의 도구가 필요한 개인… 개발 지식이 없어도 됩니다. | …나만의 도구가 필요한 사람… 개발을 몰라도 괜찮습니다. |
| 무엇을 | 기존 시스템 UX·Workflow 개선 · 업무의 웹 시스템화 · 아이디어 → MVP | 쓰던 시스템 고치기 · 엑셀과 종이로 하던 일을 웹으로 · 아이디어를 첫 제품으로 |
| Projects 패널 | 문제 유형별로 정리한 Case Study — 무엇이 불편했고 어떻게 바꿨는지. | 무엇이 불편했고 어떻게 바꿨는지 정리한 Case Study. |
| 문의 | 이 페이지의 끝이 프로젝트의 시작입니다. 2영업일 안에 답변드립니다. | 이 페이지의 끝이 프로젝트의 시작입니다. 이틀 안에 답장드리겠습니다. |
| 서랍 제목 | Prologue & 당신의 업무 | Prologue & 문의 |
| 서랍 1단계 | 현재 업무 / 현재 어떤 업무를 하고 있나요? / 가장 불편한 부분은 무엇인가요? / 사용자 수 / 반복 빈도 / 기존·신규 | 지금 하는 일 / 어떤 일을 하고 계세요? / 무엇이 가장 불편하세요? / 쓰는 사람 / 얼마나 자주 / 고치기·새로 만들기 |
| 서랍 2단계 | 목표·연락처 / 원하는 결과 (선택) / 희망 일정 / 예산 범위 | 바라는 것과 연락처 / 이렇게 됐으면 (선택) / 언제까지 / 예산 |
| 접수 | 접수됐습니다. 2영업일 안에 …로 답변드립니다. | 잘 받았습니다. 이틀 안에 …로 답장드리겠습니다. |
| 서랍 하단 | 이메일 + 문의 시트에 저장 / 2영업일 안에 답변 | 보내면 메일과 문의 목록에 남습니다 / 이틀 안에 답장 |
| Projects 리드 | 작업 기록. 브랜드명 뒤의 빈칸을 채운 것들입니다. | 지금까지 한 일. 이름 뒤의 빈칸을 채워 온 것들입니다. |
| Case Study 용어 | 구조화된 요청폼 / 심사 Queue / 약속일 / 상태 자동 공유 / 요청자 조회 / Dashboard | 요청 양식 / 심사 대기열 / 처리 예정일 / 진행 상황 자동 안내 / 요청한 사람이 직접 확인 / 현황판 |
| Insight | ToDo 관리의 문제가 아니라 요청 Workflow의 문제였습니다. | 할 일 관리가 아니라, 요청이 들어오는 길의 문제였습니다. |
| 목업 화면 | 심사 Queue / 요청자 링크 / Dashboard / 상태 공유됨 / 제출하면 심사 Queue에 들어가고, 약속일이 정해지면 | 심사 대기열 / 요청 링크 / 현황판 / 진행 상황 안내됨 / 보내면 심사 대기열에 들어가고, 처리 예정일이 정해지면 |
