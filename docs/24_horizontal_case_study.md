# Case Study 상세를 가로로 — 방식 검토

| 작성일 | 2026-09-21 |
|---|---|
| 상태 | 검토 요청. 권장 H2(세로 스크롤 → 가로 이동) + 머무름 구간, 대안 H4(경로형) |
| 전제 | 대시보드(v6)는 선이 **아래로** 흐르는 경로. 목록은 세로(짧음). 상세는 **옆으로** 읽는 축 — 축을 바꿔 "장면이 바뀌었다"를 몸으로 알게 한다. docs/23 §11의 인터랙션 D1~D8은 축만 바꿔 그대로 얹는다. 5종 상한(docs/09 §8.2) 유지 |

## 0. 축의 문법
```
대시보드   선이 내려간다 (세로 경로, 점마다 장면)          ↓
목록       세로 목록, 짧다                                 ↓
상세       옆으로 읽는다 (가로)                            →
다음 이야기 오른쪽 끝에서 다음 상세가 이어진다               → →
```
상세가 가로면 "다음 이야기"가 오른쪽 끝 다음 칸이 된다. 목록→상세는 위에서 내려오고(docs/20 A), 상세→다음 상세는 왼쪽으로 밀린다. 축이 다르니 전환도 방향이 다르다 — 이것이 가로로 바꾸는 가장 큰 이유.

## 1. 지금까지 가로에서 배운 것 (v2·v5·v6)
| 경험 | 결과 | 이번에 쓰는 법 |
|---|---|---|
| v5: Lenis 가로 모드(`orientation:'horizontal'`, `gestureOrientation:'both'`) | 고해상도 마우스에서 휠 이벤트마다 `animate.stop()`이 불려 뚝뚝 끊김. 데스크톱에서 Lenis를 빼고 자체 엔진으로 바꿈 | 가로 축을 Lenis에 맡기지 않는다 |
| v5: 자체 smoothDamp + 스냅 + 휠 스트림 감지 | 점 단위 이동은 매끄러움. 대신 연속 스크럽(진행률에 비례하는 변형)은 점 사이에서만 짧게 일어남 | 장면 단위 이동에 적합, 스크럽 인터랙션에는 약함 |
| v6: 세계 + 카메라 + 경로 | 점마다 서고, 점 사이는 곡선. 판·글자는 세계에 직접 | 브랜드 장치는 가장 강하지만 글 많은 화면엔 무거움 |
| v4: 세로 스크롤 → 가로 이동(ScrollTrigger pin) | 네이티브 세로 스크롤·Lenis 세로가 그대로. 스크럽이 자연스러움 | 읽기 화면에 가장 안전 |

## 2. 후보 다섯

### H1. 가로 스트립 + 스냅 (v5 엔진 재사용)
```
[00 표지][01 Overview][02 Problem][03 Workflow][04 Insight][05 Redesign][06 Solution][07 B&A][08 Impact][09 Learned][10 문의]
   ←  휠 한 칸 = 한 장  →      각 장 = 화면 하나(64rem × 화면 높이)
```
- 동작: v5 엔진 그대로(휠 스트림 감지 → 한 장, ←/→/J/K, 헤더 스트립 클릭, smoothDamp 0.26). 가로 스크롤바 없음.
- 장 안의 글은 화면 높이에 **맞춰야** 한다(넘치면 잘림). 한 장 = 제목 + 문단 2~3개 + 그림 하나가 상한 → 글 길이 규칙이 생긴다(docs/21과 방향은 같음).
- 스크럽(D3 morph, D5 와이프)은 03→05, 07 안에서 **장 이동 자체**가 진행률(t = 이동 비율). 장 사이를 0.8초에 지나가므로 변형이 0.8초 안에 끝난다 — 짧지만 또렷하다.
- 장점: 만들어 둔 엔진, 조작이 한 방향, 장마다 완결. 단점: 긴 글을 못 담음, 연속 스크럽이 짧음, 네이티브 스크롤이 아니라 찾기·포커스 이동을 직접 처리.

### H2. 세로 스크롤 → 가로 이동 (핀 고정, v4 방식) — **권장**
```
문서 높이 = 가로 길이.  세로로 굴리면 무대가 왼쪽으로 흐른다.
┌──────────── 화면 (pin) ────────────┐
│  01 ──── 02 ──── 03 ═══ 04 ═══ 05 ──── 06 ──── 07 ═══ 08 ──── 09 ──── 10 →  │
│              ↑ 머무름 구간(sticky): 무대는 서 있고 안의 변형만 진행           │
└─────────────────────────────────────┘
```
- 동작: `body` 세로 문서, Lenis 세로(지금 case.html 그대로). 무대(`.track`)는 `position:sticky; top:0; height:100vh`이고 `translateX = -(scrollY / (docHeight - vh)) × (trackWidth - vw)`. 스크롤바는 세로(익숙함). 트랙패드·휠·키·터치가 전부 기본 동작.
- 머무름 구간: 03~05(morph), 07(와이프)은 트랙 안에서 **가로 폭을 더 주지 않고 문서 높이만 더 준다** → 그 구간에서 무대가 멈추고 스크롤이 변형 진행률 `t`가 된다(핀 안의 핀이 아니라, 진행률→X 매핑 함수에 평평한 구간을 둔 것). 한 함수로 끝나 ScrollTrigger가 없어도 된다.
- 장 폭은 자유(글 많은 장은 넓게, 두 단). 화면 높이는 넘기지 않는다(넘치면 두 단으로).
- 헤더 스트립(D1) = 진행률. 클릭·키 이동은 `lenis.scrollTo(그 장의 문서 y)`.
- 장점: 읽기 화면에서 가장 안전(입력이 전부 기본), 스크럽이 부드럽고 길이를 정할 수 있음, Lenis 유지(5종 ①), 모바일은 pin을 풀고 같은 마크업을 세로로 쌓으면 끝. 단점: "세로로 굴렸는데 옆으로 간다"를 첫 100px에서 가르쳐야 함(v5 §5와 같은 힌트), 가로 스크롤바 없음(스트립이 대신), 문서 높이가 가짜(찾기로 점프하면 위치 계산은 되지만 어색).

### H3. 진짜 가로 문서 (overflow-x + 가로 sticky)
- 동작: `html{overflow-x:auto; overflow-y:hidden}`, 장들이 옆으로 나열. 세로 휠→가로는 직접 변환(`wheel` → `scrollBy({left})`, Lenis 없이 자체 lerp) 또는 Shift+휠·트랙패드 가로 제스처만. 머무름은 `position:sticky; left:0`(가로 sticky는 동작한다).
- 장점: 진짜 가로 스크롤바, 해시·찾기·포커스가 네이티브, 트랙패드 가로 스와이프가 그대로. 단점: 마우스 휠은 변환이 필요하고 그 변환에서 v5의 끊김이 되살아날 수 있음. Lenis를 못 쓴다(가로 모드 실패 경험) → 5종 ①의 "Lenis"가 빠짐. 마우스 사용자(병원·제조 담당자)에게 불리.

### H4. 경로형 연장 (v6 엔진 재사용, 선이 옆으로 흐름)
```
        02          04            06        08
   01 ──●────●────●────●────●────●────●────●────●── 10 →
              03          05           07        09
   완만한 굽이(위아래 ±120px). 점마다 판. 카메라는 점에서 선다.
```
- 동작: v6의 세계·카메라·점·판·잉크를 그대로, 경로만 왼→오른쪽. 세계 폭 ≈ 10장 × 900 = 9000. 대시보드에서 쓰던 휠·키·진행 지도·이동 중 축소가 같은 코드.
- 03~05 morph는 점 3개(v6 "무엇을"처럼 카메라를 가운데 점에 고정하고 선·점만 진행) 안에서, 07 와이프는 점 2개 사이.
- 장점: 브랜드 장치가 가장 강하다(S1 한 선이 상세까지 이어지고, 대시보드와 같은 손맛). 판 크기 규칙(640×420)이 그대로. 단점: 판 하나에 글이 조금밖에 못 들어감(문단 하나) → 10단계가 20점 이상으로 늘어남. 라이브 화면(1280 기준)을 판 규격 안에 넣기 어려움(세계 스케일과 글자 고정 스케일 규칙 충돌 재발). 읽기보다 보기 화면이 된다.

### H5. 두 축 혼합 (가로는 장, 세로는 장 안)
- 장(01~10)은 가로로 넘기고, 장 안의 긴 글은 세로로 굴린다.
- 장점: 글 길이 제한 없음. 단점: 축이 둘이라 "지금 어느 방향으로 굴려야 하나"를 매번 판단하게 만든다. 트랙패드에서 대각선 입력이 양쪽에 걸림. **제외.**

## 4. H2 상세 설계

### 4.1 무대와 장
```
헤더 64  Prologue& Por favor, Harry   ▬▬▬▬▬▬▬▬▬▬ (10칸)   ← Projects  03 / 10  [문의]
─────────────────────────────────────────────────────────────────────────────────────
│ 표지                 │ 01          │ 02        │ 03 ═══════ 04 ═══════ 05 │ 06             │ 07 ═══════ │ 08     │ 09  │ 10 · 다음 → │
│ 흩어진 업무 요청을    │ Overview    │ Problem   │ [다이어그램 sticky]       │ [라이브 화면]   │ [Before│After] │ Impact │ …   │ 문의 + 다음  │
│ 하나의 흐름으로       │ 문단        │ 문단      │ 03 글  04 글  05 글       │ ①②③ 캡션      │ 경계선 이동   │ 막대   │     │ 이야기       │
│ 역할·기간·사용자      │             │           │                           │                │              │        │     │              │
──●────────────────────●─────────────●───────────●═══════════●═══════════●───●────────────────●═════════════●────────●─────●──── & ──────
   선(S1): 화면 세로 62% 높이의 가로 직선. 그려진 끝 = 화면 x 50vw. 점 = 장 시작. ═ = 머무름 구간(점이 아니라 구간)
```
- 장 폭: 글 장 44rem(1단) 또는 88rem(2단), 그림 장 64~80rem. 표지 100vw. 10·다음 이야기 100vw.
- 장 높이: 헤더 아래 `100vh - 64`. 글은 상단 정렬, 그림은 세로 가운데. 넘치면 2단 — 세로 스크롤 없음.
- 무대 `.track{position:sticky; top:0; height:100vh; display:flex}` 안에 장들이 `flex:none`. 문서 높이 = `trackWidth - vw + 머무름 합`.
- 매핑 `X(scrollY)`: 구간별 선형. 보통 구간은 1px 스크롤 = 1px 이동, 머무름 구간(03~05: 160vh, 07: 120vh)은 X 고정·t만 진행. 함수 하나(`xOf(y)`)와 역함수(`yOf(x)`, 스트립 클릭용).
- 선(S1): 트랙 폭 전체의 SVG 한 줄, `stroke-dashoffset`으로 `scrollX + 50vw`까지 그려짐. 점은 장 시작 x. 지난 점은 채움(D2를 가로로).
- 진행 스트립(D1): 칸 폭 ∝ 장의 문서 높이(머무름 포함). 클릭 → `lenis.scrollTo(yOf(장 x))`.
- 키(D7): ←/→ = 이전·다음 장 시작, ↑/↓는 Lenis 기본(세로 스크롤 = 가로 이동), Home/End.

### 4.2 인터랙션 D1~D8의 가로 대응
| # | 세로 설계(docs/23 §11) | 가로에서 |
|---|---|---|
| D1 스트립 | 헤더 10칸 | 같음. 칸 폭 ∝ 구간 길이 |
| D2 레일 = 선 | 왼쪽 세로선 | **아래 가로선**(62% 높이) — 대시보드 선의 연장. 번호 레일은 없어지고 점 + 장 번호로 |
| D3 morph | sticky 다이어그램, 160vh | 머무름 구간 03~05. 다이어그램은 구간 왼쪽에 고정, 글 03·04·05는 오른쪽에 나란히(미리 다 보임). t = 구간 진행률 |
| D4 핫스팟 | 캡션 호버 → 영역 강조 | 같음. 화면이 장 폭 80rem → 라이브 화면 1.0배(1280 그대로) |
| D5 와이프 | 겹친 두 화면, 경계선 이동 | 머무름 구간 07. 경계선이 **선의 연장처럼** 왼→오른쪽. 무대가 서 있으니 경계선만 움직임 |
| D6 막대 | 08 진입 시 그려짐 | 선 끝이 08 점을 지나는 순간 그려짐(같은 진행 변수, IntersectionObserver 불필요) |
| D7 키 | ↓/↑ 항목 | ←/→ 장 |
| D8 다음 이야기 | 선이 밑줄로 | **선이 오른쪽 화면 밖으로 계속 나간다.** 10 장 오른쪽에 "다음 이야기 → Custom Commerce" 판. 클릭 시 전환은 왼쪽으로 밀림(문서 간 VT, `view-transition-name` 없이 루트를 `translateX(-40px)` 아웃 / 인) |

### 4.4 첫 100px — "옆으로 간다"를 가르치기
- 표지 장 오른쪽 아래 `→ 굴리면 옆으로` 캡션(대시보드 힌트와 같은 형식). 첫 스크롤 뒤 사라짐.
- 로드 시 선이 왼쪽에서 오른쪽으로 그려지는 것이 방향을 보여 준다(v5 §5 경험).
- 헤더 스트립이 첫 픽셀부터 같이 움직인다.
- 표지 장은 100vw라 첫 스크롤에서 표지가 왼쪽으로 밀리며 01이 들어온다 — 세로로 스크롤하는 사람이 "옆으로 가네"를 즉시 본다.

### 4.5 모바일(<1024)
- `.track{position:static; display:block}`, 장은 세로 스택, 머무름 구간은 정적(다이어그램은 Before/After 두 장, 와이프는 두 화면 나란히), 선은 왼쪽 세로 1px(기존 레일 자리). 마크업은 하나.

### 4.6 reduced-motion
- Lenis 끔, 매핑은 즉시(`X = xOf(scrollY)`를 매 프레임 그대로), 머무름 구간의 변형은 구간 중간에서 한 번에 최종 상태. 선은 즉시 그려짐.

### 4.7 데이터·문구
- 장별 폭·단 수·머무름 길이를 `case` 데이터에 둔다: `scenes:[{id:'s3', w:'88rem', dwell:160}]`. 프로젝트마다 장이 다를 수 있음(Before 화면 없는 프로젝트는 07 머무름 없음).
- 표지 H1·역할표는 지금 case-head 그대로. 글은 docs/21 규칙, 장당 문단 3개 이내(넘으면 2단).
