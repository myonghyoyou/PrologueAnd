## 2. 배치 규칙 8개

| # | 규칙 | 근거 | 우리에게 |
|---|---|---|---|
| P1 | **표지는 두 종류뿐**: 전폭 사진 + 큰 제목(ustwo·Fueled·Locomotive·라이트브레인) / 글자만 큰 문장(Instrument·Huge·Hello Monday) | 8곳 중 7곳 | 우리는 "라이브 화면"이 있으니 셋째 길이 있다 — 화면을 사진처럼 쓰는 표지 |
| P2 | **메타는 표지에 붙는다**: 표지 위 한 줄(ustwo·Locomotive) 또는 표지 바로 아래 표(Hello Monday·라이트브레인) | 전부 | 지금 case-head의 표 형식이 표준. 위치만 결정 |
| P3 | **글은 한 단, 600~700px**. 2단 본문은 없음 | 전부 | 44rem(704px) 유지 |
| P4 | **그림은 글보다 넓다**: 본문 폭을 깨고 전폭(또는 본문보다 넓은 인셋)으로 나간다 | Instrument·Huge·ustwo·Locomotive | 지금은 그림이 본문 폭(44rem) 안 → 좁다. 그림을 64~80rem이나 전폭으로 |
| P5 | **고정 요소는 헤더뿐**. 사이드바·핀 고정을 쓰는 곳이 8곳 중 0 | 전부 | 우리 번호 레일(sticky)은 에이전시 표준 밖 — 있으면 차별점이고, 없어도 표준 |
| P6 | **결과 숫자는 큰 글자 3개, 앞(ustwo) 또는 끝(Huge)** | docs/25 R2와 같음 | 표지 미리보기 + 08 |
| P7 | **끝은 다음 프로젝트**: 티저 1개(Locomotive) / 카드 3개(Hello Monday) / 캐러셀(Fueled). 없는 곳(ustwo·Huge)은 CTA만 | 5/8 | 지금 "이전·다음 이야기" 두 링크 → 티저 1개로 키우거나 카드 3개 |
| P8 | **인용·수상은 본문 중간에 한 번**, 블록으로 | Instrument·Locomotive·ustwo | 고객의 말은 안 받기로 함(docs/25). 자리만 비워 둔다 |

## 4. 안 6개

폭 기준: 본문 44rem, 그림 64rem, 전폭 = 화면. 헤더 64. `━━` 전폭 그림, `▭` 인셋 그림, `│` 고정 요소.

### A. 편집 기사형 (Editorial long-read)
```
┌───────────────────────────────────────────────┐
│ Prologue&  Por favor, Harry     ← Projects 문의 │
├───────────────────────────────────────────────┤
│        Prologue & PFH · 문제 01                 │
│        흩어진 업무 요청을                        │  H1 56px, 본문 폭
│        하나의 흐름으로                           │
│        역할 · 기간 · 사용자 · 공개 범위 (한 줄)   │  메타 한 줄 (P2)
│        4 → 1   0회   1곳                        │  숫자 미리보기 (P6)
│ ━━━━━━━━━━━━━ 라이브 화면 (전폭) ━━━━━━━━━━━━━ │  P1 셋째 길
│ 01 │  Overview  문단                            │  왼쪽 레일 = 선(S1), 번호
│ 02 │  Problem   문단                            │
│ 03 │  Existing Workflow                         │
│    │  ▭▭▭▭ 다이어그램 64rem ▭▭▭▭ (scrub)         │  그림은 본문보다 넓게 (P4)
│ 04 │  Insight  큰 문장 32px                     │
│ 05 │  Redesign 흐름 칩 + 문단                    │
│ 06 │  Solution 문단                              │
│ ━━━━━━━━━━━━━ 화면 (전폭) + 핫스팟 ━━━━━━━━━━━ │
│ 07 │  Before & After  ▭ 2단 ▭                    │
│ 08 │  Impact  4→1  0회  1곳  + 막대              │
│ 09 │  What I Learned                             │
│ 10 │  비슷한 문제가 있다면  [문의]                 │
│ ━━━━━━━━━━━ 다음 이야기: Daeryun ━━━━━━━━━━━━━ │  티저 1개 (P7)
└───────────────────────────────────────────────┘
```
- 무엇이 다른가: 지금 구조를 유지하되 (1) 표지를 글 → 전폭 화면 순서로, (2) 그림이 본문 폭을 깨고 나감, (3) 레일이 실제 선이 되어 스크롤에 비례해 그려짐, (4) 끝을 티저 1개로.
- 장점: 읽기 최적, 위험 없음, 지금 코드의 70% 재사용. 단점: 에이전시 표준과 같아 인상은 평범.

### B. 좌측 고정 요약 + 우측 흐름 (Sticky summary)
```
┌───────────────────────────────────────────────┐
│ 헤더                                            │
├──────────────┬────────────────────────────────┤
│ │ Prologue &  │  01 Overview                    │  왼쪽 22rem sticky:
│ │ PFH         │  문단                            │   제목·메타·숫자 3개·
│ │ 흩어진 요청을 │                                  │   장 목록(현재 강조)·
│ │ 하나의 흐름  │  02 Problem                     │   문의 버튼
│ │ 역할 기간    │  문단                            │
│ │ 사용자 공개  │  ━━━━ 화면 (우측 폭 전체) ━━━━   │  우측 60rem
│ │ 4→1 0회 1곳 │  03 Existing Workflow            │
│ │ 01 02 03 04 │  ▭ 다이어그램 ▭                   │
│ │ 05 06 07 08 │  04 Insight                      │

```
- 무엇이 다른가: 표지가 없다. 요약(제목·메타·숫자·목차)이 왼쪽에 **계속 보이고**, 오른쪽만 흐른다. 대시보드의 "판" 감각(왼쪽 판 하나가 붙어 있음)과 통한다.
- 장점: 어디를 읽어도 맥락(무슨 프로젝트·결과)이 보임. 목차 = 진행 표시. 단점: 에이전시 표준 밖(P5), 우측 폭이 줄어 그림이 전폭이 못 됨(≈60rem), 모바일은 A로 풀어야 함. 시트 폭(56rem)에는 안 들어감 → 전면 페이지 전용.

### C. 화면 우선 쇼케이스 (Media-first)
```
┌───────────────────────────────────────────────┐
│ 헤더                                            │
│ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ │
│ ━━━━━━━━━ 라이브 화면, 화면 높이 80% ━━━━━━━━━━ │  표지 = 화면 (P1 셋째 길)
```

- 무엇이 다른가: 글이 캡션이 되고 화면이 본문이 된다. 장마다 그림 하나가 필수 → 스키마의 `screen/before/after/hero`가 모두 채워져야 함.
- 장점: "만든 것"이 바로 보임, 인상 강함(Metalab·Instrument 계열). 단점: **라이브 화면이 있는 프로젝트가 1개**. 나머지 3개는 정지 이미지 1장씩이라 이 안이 성립하지 않는다 → 프로젝트마다 화면 3~4장을 먼저 만들어야 함. 글이 줄어 "문제 → 워크플로 → 제품 → 영향" 서사가 약해짐.

### D. 스크롤 텔링 (Pinned media + steps)
```
┌───────────────────────────────────────────────┐
│ 헤더                                            │
│   표지: 제목 + 메타 + 숫자 (A와 같음)             │
├────────────────────────┬──────────────────────┤
│  01 Overview 문단       │ │                     │  오른쪽 40%: 고정(sticky)
│  02 Problem 문단        │ │  [현재 장의 그림]     │   장이 바뀌면 그림이 교체
│  03 Existing Workflow   │ │   01·02: 화면        │   03→05: 다이어그램 morph
│  04 Insight             │ │   03~05: 다이어그램   │        (scrub, 글 위치 = t)
│  05 Redesign            │ │   06: 양식 + 핫스팟   │   07: Before→After 와이프
│  06 Solution 캡션 3     │ │   07: 와이프          │   08: 막대
│  07 Before & After      │ │   08: 숫자 막대       │
│  08 Impact              │ │                     │
│  09 · 10                │ │  (10에서 해제)        │
├────────────────────────┴──────────────────────┤
│ ━━━━━━━━━━━ 다음 이야기 ━━━━━━━━━━━━━━━━━━━━━━ │
└───────────────────────────────────────────────┘
```
- 무엇이 다른가: 글은 왼쪽 한 단으로 흐르고, 오른쪽 그림이 **붙어서** 장에 맞춰 바뀐다. 가로 시안에서 만든 morph·와이프·핫스팟·막대가 그대로 "오른쪽 판"의 상태가 된다.
- 장점: 인터랙션이 가장 많이 살아남음(docs/23 §11 D1~D8 거의 전부), 한 화면에 글과 그림이 항상 함께. 단점: 그림이 화면의 40%(≈560px)로 작다(P4 위반), 핀 고정 구간이 길어 5종 상한의 "핀"이 사실상 하나 더 생김(docs/14 "핀 고정 없음"과 충돌 → 결정 필요), 모바일은 A로.

- 장점: 포스터 문법(docs/18)과 큰 타이포, 대시보드와 통일감. 단점: 글이 한 장 안에 들어가야 함(H1 안과 같은 제약), 스냅 스크롤은 읽기 화면에서 피로(v5에서 확인), Lenis와 스냅 충돌(`lenis/snap` 플러그인 필요). "읽는 상세"라는 전제(docs/24 §3)와 어긋남.

## 6. 권장 조합과 이유

**F + H3 · M2 · R2 · N3 · W2 · I3 · B1 · E2**.

1. 대시보드(판 + 선 + 진행 지도)와 상세가 같은 부품을 쓴다. 시트를 없애든 남기든 성립한다.
2. 에이전시 배치 규칙 P2·P3·P4·P6·P7을 그대로 만족하고, 우리만의 것(S1 레일, 번호, 표지 판)이 그 위에 얹힌다.
3. 인터랙션은 5종 안: Lenis+레일 잉크(①), 다이어그램 morph(⑤), 핫스팟 호버, 서랍, VT. 핀 고정 없음.
4. 프로젝트 4개가 같은 틀: 화면이 없으면 표지 그림 판과 06 그림이 정지 이미지로, 07은 2단 중 한쪽이 03의 다이어그램.

대안: 인상을 더 원하면 **D**(핀 고정 그림)를, 글을 줄이고 화면을 늘릴 계획이면 **C**. 둘 다 "핀 없음"·"화면 1개뿐"이라는 현재 조건과 충돌하므로 조건이 바뀔 때 다시 본다.
