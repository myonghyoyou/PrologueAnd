## 2. 사이트별 관찰

### 2.1 Linear — "절제의 기준점"
- **화려한 부분**: 스크롤에 따라 긴 문장이 단어 단위로 어두운 회색에서 흰색으로 밝아지는 텍스트 리빌. 히어로 아래 제품 화면이 **이미지가 아니라 실제 HTML**로 렌더링돼 텍스트 선택·확대가 됨.
- **간결한 부분**: 헤드라인은 아무 모션 없이 즉시 보임. 배경 효과·파티클·커서 장식 없음. 섹션 페이드인 없음.
- **기술**: 외부 애니메이션 라이브러리 없음(GSAP·Lenis 미검출). 캔버스·영상 0.
- **Prologue&에 가져올 것**: 헤드라인 즉시 표시, 텍스트 리빌 1회, 제품 화면을 실제 HTML로 재구성(3안 시안에서 이미 시도한 방식).
- **버릴 것**: 다크 기본 톤(주 고객 가독성).

### 2.2 Stripe — "배경 하나로 브랜드 만들기"
- **화려한 부분**: 히어로 배경의 WebGL 그라데이션 띠(캔버스 2개)가 천천히 흐름. "Global GDP running on Stripe: 1.71577580%" 실시간 카운터.
- **간결한 부분**: 히어로 텍스트는 정적. 카운터 하나가 "살아 있음"을 전달.
- **기술**: Next.js, 자체 셰이더. 1.3MB로 가벼움.
- **가져올 것**: "살아 있는 숫자" 1개 — 예: 접수된 문의 수, 최근 배포일 같은 실제 데이터. 다만 초기에는 데이터가 없어 v2 항목.
- **버릴 것**: 셰이더 그라데이션은 2025년 이후 상용화(Vercel v0 템플릿에도 있음)돼 차별성이 없고 로고 톤과도 맞지 않음.

### 2.3 Family — "마이크로 인터랙션을 영상으로"
- **화려한 부분**: 히어로에 떠다니는 일러스트 캐릭터. 본문 기능 설명이 전부 앱 조작 영상(9개)으로 재생됨.
- **간결한 부분**: 텍스트 설명이 짧고, 영상이 설명을 대신.
- **기술**: 영상 9개, 총 14.9MB — 검토 대상 중 가장 무거움.
- **가져올 것**: "기능을 말로 설명하지 말고 동작을 보여준다"는 원칙. 단 영상 대신 SVG/HTML 애니메이션으로.
- **버릴 것**: 영상 의존(용량·NDA·제작 공수 모두 불리).

### 2.4 Raycast — "제품 속도 = 사이트 속도"
- **화려한 부분**: 히어로의 붉은 사선 노이즈 배경(캔버스 1개). 스크롤하면 macOS 데스크톱 프레임 안에서 실제 런처 UI가 조작되는 장면.
- **간결한 부분**: 전환이 전부 짧고(200ms 안팎) 스크롤을 방해하지 않음. 스무스 스크롤 라이브러리 없음.
- **기술**: Next.js, 2.9MB.
- **가져올 것**: 전환 속도 기준(150~250ms), 데스크톱 프레임 안의 제품 시연.
- **버릴 것**: 다크 + 단일 네온 액센트(포화 패턴).

### 2.5 토스 — "국내 스크롤텔링의 표준"
- **화려한 부분**: 영상 히어로가 둥근 카드에서 전체 화면으로 확장 → 스크롤에 따라 3D 폰이 회전하며 장면 전환 → 화면 왼쪽에 섹션 진행 표시선. 총 5만px 이상의 스크롤 서사.
- **간결한 부분**: 한 화면에 문장 1개. 카피가 짧고 큼("금융부터 일상까지, 마침내, 토스 하나로").
- **기술**: Next.js + **Lenis**(스무스 스크롤). 캔버스 1, 영상 1, 4.8MB.
- **가져올 것**: 왼쪽 진행 표시선(Case Study 10단계에 그대로 맞음), 한 화면 한 문장 원칙, 핀 고정 장면 전환.
- **버릴 것**: 5만px 스크롤 길이(포트폴리오 방문자는 2~3분 안에 문의 여부를 판단함), 실사 영상.

### 2.6 Apple iPhone 18 Pro — "스크롤에 묶인 영상"
- **화려한 부분**: 영상 14개를 스크롤 위치에 맞춰 재생(scrub). 문단 안에서 핵심 구절만 흰색으로 강조. 상단에 제품명 + 구매 버튼 바가 고정.
- **간결한 부분**: 외부 라이브러리 없음. 리소스 53개로 오히려 적음.
- **기술**: 자체 구현, 3.9MB.
- **가져올 것**: 문단 내 핵심 구절 강조(Insight 문장에 적용), 상단 고정 바(Case Study에서 "프로젝트명 + 문의하기").
- **버릴 것**: 영상 스크럽(제작 불가).

### 2.7 Rauno Freiberg — "0.6MB로 만드는 강한 인상"
- **화려한 부분**: 세로 휠을 돌리면 카드가 **가로로** 이동. 상단에 필름 스트립 모양 진행 표시. 십자(+) 커스텀 커서. 원형 도형이 글자와 겹치는 대담한 구성.
- **간결한 부분**: 리소스 34개, 0.6MB. 캔버스·영상 0. 인터랙션 종류가 3개뿐인데 전부 기억에 남음.
- **기술**: Next.js.
- **가져올 것**: "종류를 줄이고 하나를 끝까지" 원칙. 진행 표시를 장식이 아닌 내비게이션으로 쓰는 방식.
- **버릴 것**: 가로 스크롤(B2B 방문자에게 낯설고 모바일 불리), 커스텀 커서(터치 기기 무의미).

### 2.8 Lusion — "화려함의 상한선"
- **화려한 부분**: WebGL 3D 물리 장면(십자 블록이 굴러다님), 가상 스크롤, "SCROLL TO EXPLORE" 별표 회전.
- **간결한 부분**: 화면에 텍스트가 거의 없음.
- **기술**: 자체 WebGL, 캔버스 3개. **프리로더가 약 15초** 동안 84%에 머묾.
- **가져올 것**: 없음. 기준점으로만.
- **버릴 것**: 프리로더, 3D 파이프라인(공수·성능·주 고객 기기 모두 불리).

### 2.9 투워즈 towards.co.kr — "원페이지 서비스 랜딩의 국내 모범"

사용자 요청으로 상세 검토. 데스크톱 1440px에서 8장, 모바일 400px에서 3장 캡처하고 DOM을 직접 확인했다.

**페이지 구조 (한 페이지, 7,035px)**
1. Hero — 검정 배경, 대형 Poppins "we are working towards what's next." + 깜빡이는 주황 타이핑 커서, 아래에 ASCII 아트로 렌더링된 형상
2. 소개 문장 — "투워즈는 브랜드의 방향을 같이 찾고, 웹으로 완성하는 스튜디오입니다. 감도 있는|" (타이핑 진행 중 상태로 보임)
3. Featured Work — GRID / LIST 토글, 카드 4개(카테고리 | 이름)
4. Process — 01 Consultation → 02 Reference → 03 Main Draft → 04 Full Draft → 05 Build(아임웹 구축) → 06 Launch. 각 단계 아래 **칩**("핵심 단계", "피드백 1회", "SEO 기본 설정 포함", "오픈 후 하자 무상")
5. "이 모든 과정이 평균 2~4주" + 검정 CTA "프로젝트 시작하기"

7. 푸터 — 화면 폭을 채우는 대형 워드마크 "towards."

**디자인 언어**: 오프화이트 `#F7F5F2` / 잉크 검정 / 주황 `#FF4D2E` 단일 액센트. Poppins(라틴) + Pretendard(한글) 볼드. 히어로만 검정으로 반전. 본문 콘텐츠를 화면 **중앙선에서 시작**시켜 오른쪽 절반에 배치 — 십자선의 세로선과 맞물려 "조준선" 인상을 만든다.

**기술**: 아임웹(imweb) 빌더 위에 커스텀 코드. jQuery·Bootstrap·lodash·axios 등 빌더 기본 스크립트가 함께 로드(리소스 157개). 채널톡, YouTube API, Datadog RUM 포함. `<h1>` 없음.

**강점**
- 인터랙션이 사실상 4종(십자선·ASCII·타이핑·Lenis)이고 전부 "towards = 방향·조준"이라는 브랜드 은유에 묶여 있다. Rauno와 같은 "종류는 적게, 하나는 끝까지" 원칙.
- Process 섹션의 칩이 고객의 불안(견적 기준, 수정 횟수, SEO 포함 여부, 하자 처리)에 즉답한다. B2B 전환 관점에서 검토 사이트 중 가장 실용적.
- 원페이지 7,000px — 방문자가 2~3분 안에 회사·작업·프로세스·서비스를 다 보고 문의 버튼에 닿는다.
- 검정 히어로 1섹션만 반전해 첫인상은 강하게, 본문은 밝게 읽히게.

**약점**
- 빌더 스크립트 부담(리소스 157개)으로 첫 로드가 무겁다.
- 십자선이 본문 텍스트 위를 지날 때 가독성이 미세하게 떨어진다. 모바일에서는 의미 없이 중앙에 남는다.
- 플로팅 요소 3개(GIF·채널톡·LUCKY BTN)가 서로 겹친다.
- `<h1>` 부재, 아임웹 구조로 SEO 통제 한계.

**Rauno와의 비교**: 둘 다 "커서/십자선 + 정적 대형 타이포 + 적은 종류의 인터랙션 + 진행 표시"라는 같은 계열이다. 차이는 목적 — Rauno는 작품 감상용 가로 갤러리, 투워즈는 문의 전환용 원페이지 서비스 랜딩. **Prologue&의 목적(문의 전환)에는 투워즈의 구조가, 인상의 밀도에는 Rauno의 절제가 맞는다.**

**Prologue&에 가져올 것**
1. Process 단계별 "고객 불안 즉답 칩" — How Prologue& Works 5단계와 Services에 적용(예: "범위 확정 후 추가 견적 없음", "화면 공개 불가 시 Mockup으로 대체")
2. 커서 십자선 — 로고의 facet 선 문법으로 재해석. 데스크톱 전용, 텍스트 위에서는 투명도 30%, 클릭 가능한 요소 위에서 "보기" 라벨
3. GRID / LIST 토글(Work 목록)
4. 원페이지 길이 감각(Home 7,000~9,000px)과 검정 히어로 1섹션 반전은 시안 확정 시 선택지로
5. 핵심 문장만 액센트 색으로 강조(Insight 문장)

**버릴 것**: ASCII 영상(영상 자산 없음, 브랜드 톤 불일치), LUCKY BTN·GIF 같은 장난 요소(B2B 신뢰), 빌더 의존.

참고: `03_project_case_studies.md`에서 Custom Commerce를 "아임웹 등 완성형 프레임워크 없이 직접 구축"으로 차별화하는데, 국내 스튜디오의 대표 사이트조차 아임웹 위에 커스텀 코드를 얹어 만든다는 사실은 그 차별화 문장의 근거로 쓸 수 있다.

## 3. 공통 패턴 — "간결하면서 화려한" 사이트의 공식

1. **화려함은 한 곳에 몰아 쓴다.** 8개 사이트 모두 기억에 남는 장치는 1~2개다(Linear 텍스트 리빌, Stripe 그라데이션, 토스 폰 회전, Rauno 가로 이동). 나머지 섹션은 정적이다.
2. **헤드라인은 즉시 보인다.** 어떤 사이트도 H1을 페이드인으로 숨기지 않는다. 등장 애니메이션은 헤드라인 주변 요소에만.
3. **모션이 내용을 설명한다.** Apple의 영상, Family의 앱 조작, 토스의 폰 화면은 장식이 아니라 "이 제품이 이렇게 동작한다"는 설명이다. 설명하지 않는 모션은 없다.
4. **스크롤이 타임라인이다.** 시간 기반 자동 재생보다 스크롤 위치에 묶인 진행(scrub)이 많다. 사용자가 속도를 통제하므로 "화려한데 답답하지 않다".
5. **제품 화면은 이미지가 아니다.** Linear·Raycast·Stripe는 UI를 HTML로 다시 그리거나 프레임 안에서 실제로 조작한다. 스크린샷은 최후 수단.
6. **전환은 200ms 안팎.** Raycast·Linear의 호버·전환은 짧다. 긴 이징은 핀 고정 장면에서만.
7. **진행 표시가 내비게이션이다.** 토스(세로 선), Rauno(필름 스트립), Apple(고정 바)은 "어디까지 왔고 어디로 갈 수 있는지"를 항상 보여준다.
8. **무게와 화려함은 비례하지 않는다.** Rauno 0.6MB, Stripe 1.3MB, Apple 리소스 53개. 가장 무거운 Family(14.9MB)가 가장 화려하지는 않다.

## 4. Prologue&에 적용할 인터랙션 설계안

포지셔닝("복잡한 업무를 단순한 제품으로")을 모션 자체가 설명하도록 설계한다. 디자인 5안 중 어느 것이 확정되든 아래 구조는 유지하고, 시각 스타일만 안에 맞춘다.

### 4.1 페이지별 인터랙션 지도

| 위치 | 인터랙션 | 종류 | 참고 사이트 | 설명력 |
|---|---|---|---|---|
| **Home Hero** | (1) 로드 시 헤드라인은 즉시, 서브·CTA는 80ms 간격 등장. (2) 로고의 `&` 안 면분할 선 문법으로 "엉킨 4개 선"이 그려진 뒤, **스크롤 첫 100vh 동안 선이 풀려 하나의 직선 + 삼각 플래그로 정리됨**(scrub) | 로드 시퀀스 + 스크롤 연동 | Apple(scrub), Linear(즉시 표시) | 브랜드 문장을 그림으로 증명 |
| **Problems I Solve** | 4개 항목 각각에 호버/탭하면 6초 SVG 루프 재생: 흩어진 아이콘 → 정렬. 터치 기기에서는 뷰포트 진입 시 1회 재생 | 마이크로 데모 | Family(동작으로 설명), 영상 대신 SVG | 방문자가 자기 문제를 "보고" 찾음 |
| **Featured Work** | 카드 안에 각 프로젝트의 핵심 화면을 **HTML로 재구성**해 축소 표시. 호버 시 상태가 한 단계 진행(예: 심사 대기 → 수락) | 실제 UI 미니 데모 | Linear, Raycast | "만들 수 있는 사람"을 증명 |
| **How Prologue& Works** | 5단계를 핀 고정. 스크롤할 때마다 단계가 넘어가고 옆의 다이어그램이 Understand → Simplify → Design → Build → Improve 순으로 변형. **페이지에서 유일한 핀 고정 구간** | 핀 고정 스크롤텔링 | 토스 | 일하는 방식 설명 |
| **Services / About** | 모션 없음. 호버 밑줄·버튼 200ms 전환만 | — | Raycast(속도) | 읽는 구간 |
| **Contact** | 폼 2단계 전환을 슬라이드로, 제출 후 버튼이 "접수됨" 상태로 변형(페이지 이동 없음) | 응답형 모션 | Raycast | 사용자 행동에 대한 피드백 |
| **Case Study** | (1) 왼쪽에 10단계 진행 표시선(클릭 이동 가능). (2) 상단 고정 바 "프로젝트명 + 문의하기". (3) Existing Workflow → Redesign 구간에서 **Before 다이어그램이 스크롤에 따라 After로 변형**(scrub). (4) Insight 문장은 핵심 구절만 강조색 | 진행 표시 + 스크롤 연동 | 토스(진행선), Apple(고정 바·구절 강조) | Case Study의 핵심 주장을 모션이 증명 |
| **페이지 전환** | View Transitions API로 Work 카드 → Case Study 상세로 갈 때 카드 이미지가 확대돼 히어로가 됨 | 공유 요소 전환 | (네이티브) | 사이트가 한 덩어리로 느껴짐 |

### 4.2 하지 않는 것
- 섹션마다 페이드업, 카드마다 호버 확대 — 8개 사이트 어디에도 없고 AI 생성 티의 대표

### 4.3 화려함 예산 (지키지 못하면 모션을 줄인다)

## 5. 기술 선택

| 용도 | 선택 | 근거 |
|---|---|---|
| 로드 시퀀스, 호버·버튼 전환 | **CSS** (`@keyframes`, `transition`) | JS 불필요, 헤드라인 즉시 표시 보장 |
| 히어로 선 정리·Case Study 다이어그램 변형(scrub), How it Works 핀 고정 | **GSAP 3 + ScrollTrigger** (`useGSAP` 훅) | 2025년 4월부터 전 플러그인 무료(상업용 포함). pin·scrub·timeline이 가장 안정적. Apple·토스급 장면을 SVG로 구현 가능 |
| 뷰포트 진입 1회 재생, 폼 상태 전환 | **Motion** (`motion/react`, 구 Framer Motion) 또는 GSAP 재사용 | 둘 중 하나로 통일. GSAP를 쓰기로 했으면 Motion은 추가하지 않음 |
| 스크롤 연동 중 단순한 것(히어로 페이드) | **CSS scroll-driven animations** (`animation-timeline: view()`) + `@supports` 폴백 | Chrome/Edge/Safari 26 지원, Firefox 안정판은 아직 플래그. 점진적 향상으로만 사용 |
| 페이지 전환 | **View Transitions API** (Next.js `next-view-transitions` 또는 실험 플래그) | 네이티브, 미지원 브라우저는 일반 전환 |
| SVG 다이어그램 | React 컴포넌트로 작성, 상태(step)를 prop으로 받아 GSAP가 보간 | Before/After를 하나의 SVG로 두고 좌표만 변형해야 scrub이 자연스러움 |

Next.js App Router에서는 모션이 필요한 컴포넌트만 `"use client"`로 두고, 다이어그램 SVG 자체는 서버 렌더링해 JS 없이도 보이게 한다.

## 8. 방향 결정 (2026-09-15, 사용자 결정) — Rauno 계열 + Lenis

사용자가 검토 결과 중 **Rauno Freiberg 사이트를 가장 선호**했고, **Lenis 스무스 스크롤 포함**을 요청했다. 이에 따라 §4의 설계안을 아래처럼 조정한다. §4.2에서 제외했던 "커스텀 커서·스무스 스크롤"은 이 결정으로 **허용 항목**이 된다.

### 8.1 Rauno 계열이 뜻하는 것
- 인터랙션 **종류를 적게**(사이트 전체 5종 이하) 두고, 각각을 끝까지 다듬는다
- 가볍다(Rauno 0.6MB) — 영상·WebGL 없이 타이포·도형·SVG로만
- 진행 표시가 장식이 아니라 내비게이션이다
- 도형과 타이포가 대담하게 겹친다 — Prologue&에서는 로고의 `&`를 히어로에서 대형 장식으로 1회 사용

### 8.2 사이트 전체 인터랙션 5종 (이 밖에는 추가하지 않는다)
| # | 장치 | 출처 | 적용 위치 |
|---|---|---|---|
| 1 | **Lenis 스무스 스크롤 + 진행 표시** | 사용자 요청 / Rauno 필름 스트립 / 토스 세로선 | 전체. Home은 7섹션, Case Study는 10단계를 상단 얇은 스트립으로 표시하고 클릭하면 `lenis.scrollTo`로 이동 |
| 2 | **커서 십자선** | 투워즈 / Rauno | 데스크톱 전용. 로고 facet 선 굵기(1px 스틸블루), 텍스트 위 투명도 30%, 클릭 가능 요소 위에서 삼각 플래그 + "보기" 라벨 |
| 3 | **히어로 선 정리(scrub)** | §4.1 유지 | 로드 시 엉킨 4개 선이 그려지고, 스크롤 첫 100vh 동안 하나의 직선 + 삼각 플래그로 정리 |
| 4 | **How Prologue& Works 핀 고정** | 토스 | 5단계 + 투워즈식 "고객 불안 즉답 칩". 페이지 유일의 핀 구간 |
| 5 | **Case Study 다이어그램 변형(scrub)** | §4.1 유지 | Existing Workflow → Redesign. 상단 고정 바(프로젝트명 + 문의하기) 포함 |

v2로 미루는 것: Problems 호버 SVG 루프, Featured Work 카드 호버 상태 진행, View Transitions 페이지 전환. 5종이 자리 잡은 뒤 하나씩 추가 여부를 판단한다.

### 8.3 Lenis 적용 규칙
- 설정: `lerp: 0.1` (또는 `duration: 1.2`, easing 기본), `wheelMultiplier: 1`, `syncTouch: false`(iOS·Android는 네이티브 스크롤 유지)
- `prefers-reduced-motion: reduce`면 Lenis를 초기화하지 않는다
- GSAP ScrollTrigger 연동: `lenis.on('scroll', ScrollTrigger.update)` + `gsap.ticker.add(t => lenis.raf(t * 1000))`, `gsap.ticker.lagSmoothing(0)`
- 앵커·진행 표시 클릭은 `lenis.scrollTo(target, {offset: -헤더높이})`
- 핀 고정 구간(4번)은 Lenis 위에서 ScrollTrigger `pin`이 정상 동작하는지 시안에서 먼저 검증. 어색하면 핀 구간만 `pinType: 'transform'`으로 전환
- 번들: Lenis 약 3KB gz — §4.3 예산(애니메이션 JS 60KB) 안에 포함

### 8.4 화려함 예산 조정
| 항목 | 기존 | 변경 |
|---|---|---|
| 커스텀 커서 | 금지 | 데스크톱 전용 십자선 허용, 터치 기기에서는 DOM 자체를 렌더링하지 않음 |
| 스무스 스크롤 | v1 제외 | Lenis 채택 |
| 인터랙션 종류 | 명시 없음 | **사이트 전체 5종 상한** |
| 그 외 | §4.3 유지 | — |

### 8.5 시안 반영 순서
1. 2안(블루프린트) 시안에 Lenis + 진행 표시 + 커서 십자선 + 히어로 scrub + 핀 고정 5종을 전부 넣어 데스크톱·모바일에서 확인
2. 채택되면 나머지 안에는 같은 5종을 스타일만 바꿔 적용
3. `08` §5.3 기준으로 재평가 후 디자인 방향 확정
